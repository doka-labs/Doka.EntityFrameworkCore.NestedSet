# Query composition regression coverage

This map connects all 160 reviewed contract IDs to concrete tests: 89 generic
library contracts, nine SignalLab consumer contracts and 62 UserGroups contracts. The IDs are
traceability labels. They do not require 160 methods, duplicate pure rules on
five providers, or turn consumer policies into NestedSet APIs.

[Query composition](query-composition.md) owns the library behavior;
[D-018](decisions/D-018-generic-hierarchy-query-composition.md) owns the boundary.
The [SignalLab](../samples/SignalLab/README.md) and
[UserGroups](../samples/UserGroups/README.md) guides own their application rules.
Existing mutation and typed-runtime regressions remain in the
[original coverage guide](regression-coverage.md).

The [implementation source map](implementation-design.md#source-layout) locates
the focused query and consumer partials. Those file boundaries do not change
the contract IDs below or turn consumer policies into product behavior.

## Reading the evidence

- Unit tests verify pure request, selection, expression and pre-I/O rejection
  contracts once. They use the actual sample assemblies where applicable.
- Shared specification tests execute through provider-owned fixtures in the
  MySQL, MariaDB, PostgreSQL, SQLite and SQL Server suites. A source reference
  alone is not evidence that all five engines executed successfully.
- Capacity tests reuse persisted structural populations; actual consumer
  builders and bounded payload are additional assertions on that population.
- Exact command counts, tuple bags, parameters, tracking, cancellation and
  before/after snapshots matter more than a successful translation alone.

The table is a source-coverage map. Execution qualification requires its own
explicit source boundary. The historical record below retains the remaining
native SQL Server boundary without qualifying later changes.
Every listed source contract has a corresponding semantic test. Qualification
of the complete large-profile and native-provider matrix is a separate result.

### Final adopted source

The adopted optional contract is the generated structural index plus eligible
source binding, with an independent ordered-edge requirement for inclusive
queries. Its [qualification summary](qualification/query-composition.md#optional-ancestor-access)
retains the frozen provider/product identities, complete native cohorts,
write/storage costs and unfavorable reads. Compiled models independently
require strict binding with source-only capability, correct inclusive fallback
without an ordered edge, and two directed inclusive edges when both APIs exist.
The strict indexed path remains free of ordered edges. Each public ordered-join call
supplies one edge; the inclusive library strategy invokes it for structural
matching and final owner hydration. SQL shape alone is not native work evidence.

The endpoint/visibility allocation controls retain their unchanged budgets and
adversarial provenance cases. Their [measurement boundary](performance.md#endpoint-provenance-construction)
is operation-local construction, not database execution or whole-consumer
allocation. Earlier counts do not qualify a later selection, provider or
compiled-model change.
